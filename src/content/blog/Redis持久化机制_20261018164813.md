Redis是**内存级数据库**，但如果一直把数据放在内存，<u>崩溃/断电/关机时就会消失</u>，因此为了重启Redis后仍然能够加载以前的数据，就需要将Redis的数据写入磁盘，这个过程就叫做`持久化`。
Redis的持久化机制有两种：`RDB(redis database)`和`AOF(append only file)`，可以选择只用RDB/AOF，不用持久化，或RDB+AOF
- RDB：通过**快照**（snapshot）机制，定期把某一时刻的内存数据保存下来
- AOF：记录对Redis执行的**命令**，恢复时重新执行这些命令
![RDB与AOF](image/Redis持久化机制_20261018164813/RDB与AOF.webp)


# RDB
通过RDB保存的数据，会变为一个叫dump.rdb的文件，当Redis启动时，就会**读取这个文件内的数据到内存**
触发RDB的方式有**自动触发**和**手动触发**
## 自动触发
Redis可以**根据时间和数据库修改次数**，自动触发RDB，具体配置在redis.conf文件中

```bash
 ################################ SNAPSHOTTING  ################################
 
 # Save the DB to disk.
 #
 # save <seconds> <changes> [<seconds> <changes> ...]
 #
 # Redis will save the DB if the given number of seconds elapsed and it
 # surpassed the given number of write operations against the DB.
 #
 # Snapshotting can be completely disabled with a single empty string argument
 # as in following example:
 #
 # save ""
 #
433 # Unless specified otherwise, by default Redis will save the DB:
 #   * After 3600 seconds (an hour) if at least 1 change was performed
 #   * After 300 seconds (5 minutes) if at least 100 changes were performed
435 #   * After 60 seconds if at least 10000 changes were performed
 #
 # You can set these explicitly by uncommenting the following line.
 #
439 # save 3600 1 300 100 60 10000
 
 # By default Redis will stop accepting writes if RDB snapshots are enabled
 # (at least one save point) and the latest background save failed.
```
在433~435行，就是Redis默认的配置规则介绍，439是默认配置规则，即使不显式定义也会是默认行为
当前默认规则，机翻过来是：若，

> 在一小时（3600秒）内，至少执行了1次更改 
> 在300秒（即5分钟）内，至少执行了100次更改 
> 在60秒内，至少执行了10000次更改

就会自动触发RDB
### 详细理解
对于`SAVE 5 2`，意思为
1. 距离上一次成功生成 RDB 快照，已经经**过至少 5 秒**。
2. 自上一次成功生成 RDB 快照以来，数据库**至少发生了 2 次变更**。
**两个条件都满足就会触发RDB**

### 修改配置
rdb文件的存储路径为redis的工作目录，默认为`./`
修改就在redis.conf中找到working directory，`dir`后就是工作目录
```bash
# The working directory.
#
# The DB will be written inside this directory, with the filename specified
# above using the 'dbfilename' configuration directive.
#
# The Append Only File will also be created inside this directory.
#
# Note that you must specify a directory here, not a file name.
dir /var/lib/redis
```

rdb文件默认名为dump.rdb，若要修改，就找到下面这行，`dbfilename`后即为文件名
```bash
# The filename where to dump the DB
dbfilename dump.rdb
```
上面这种修改配置文件的操作也可以在redis-cli中，用`CONFIG GET key`或`CONFIG SET key value `获取/写入配置，但这种方法修改的是正在运行的Redis配置，**重启后会恢复**（可以用`CONFIG REWRITE`尝试将当前生效的配置写回 Redis 启动时使用的配置文件）

在实际生产环境中不可以把备份文件dump.rdb和生产redis服务器放在同一台机器，必须**分开各自存储**，以防生产机物理损坏后备份文件也挂了

另外，Redis 执行`SHUTDOWN`时，如果配置了 RDB 保存条件，默认**会同步保存 RDB**；如果启用了 AOF，也会刷新并同步 AOF。执行`FLUSHALL`时，如果配置了 RDB 保存条件，会**立即保存一次 RDB**，以记录所有数据库清空后的状态。`FLUSHDB`**不会专门立即触发 RDB 保存**，其持久化行为取决于 AOF 和后续 RDB 保存机制。
## 手动触发
自动触发是被动触发，若某一时刻不满足RDB条件，但现在就是要备份，就需要用到手动触发
手动触发有两个命令：`BGSAVE`和`SAVE`
- `BGSAVE`命令会**fork一个子进程**，让子进程将快照写入 RDB 文件，而主进程可以继续执行其他命令（**异步**）
- `SAVE`命令用主进程负责RDB工作，即在RDB完成之前，不能执行其他命令操作（**阻塞**），该命令一般只有当`BGSAVE`无法fork子进程时才会作为最终手段使用

## RDB优缺点
优点：
1. **文件紧凑**，占用磁盘空间通常较少
2. 恢复大型数据集通常较快
3. 适合定期备份、异地备份

缺点：
1. 两次快照之间的数据可能**丢失**
2. 若数据集过大，生成快照时 fork() 后会占用两倍的内存
3. 内存数据的全量同步，如果数据量太大会导致I/O严重影响服务器性能

若想**禁用RDB**，在配置文件中显式设置`save ""`即可
## 总结触发RDB的情况
1. 满足redis.conf中的save条件
2. `SHUTDOWN`终止redis-server且没有开启`AOF`持久化时
3. `FLUSHALL`清空数据库
4. `SAVE`/`BGSAVE`命令
5. 主从复制时，主节点自动触发

# AOF
因为RDB并不完美，服务端非正常手段终止时，会丢失最新一次RDB后的数据，因此就有了AOF。

AOF以日志的形式记录每个**写操作**，将Redis执行过的所有写命令记录下来（读操作不记录），**只追加文件**但不改写文件。在redis-cli启动时会**读取该日志文件内容从前到后执行指令以重新构建数据**（类似.sql文件）

默认情况下Redis关闭了AOF功能，开启需要在redis.conf中设置`appendonly yes`
## AOF工作流程
![AOF工作流程](image/Redis持久化机制_20261018164813/AOF工作流程.png)
- 当有写命令到达Redis时，并不会直接写入AOF文件，而是**先将命令放入AOF缓存区**，再根据AOF的**写回策略**将命令写入磁盘的AOF文件
- 随着AOF文件内容的增加，为了避免文件膨胀，会根据规则进行命令的合并（**AOF重写**），从而压缩AOF文件
- 当redis-server启动时，就从AOF文件中载入数据

### AOF写回策略
AOF的写回策略有三种：`always`、`everysec`、`no`
- always：每个写命令执行完后立即同步到磁盘，**性能开销最大，数据丢失风险最低**
- everysec：每秒同步到磁盘一次，**性能和数据丢失风险平衡**
- no：不主动同步，而是让操作系统自行决定何时将缓存中的数据刷到磁盘，**性能开销最低，数据丢失风险最大**

| 配置项      | 写回时机      | 优点           | 缺点               |
| -------- | --------- | ------------ | ---------------- |
| Always   | 同步写回      | 可靠性高，数据基本不丢失 | 每个写命令都要落盘，性能影响较大 |
| Everysec | 每秒写回      | 性能适中         | 宕机时丢失 1 秒内的数据    |
| No       | 操作系统控制的写回 | 性能好          | 宕机时丢失数据较多        |

Redis**默认的写回策略**为`everysec`
### 修改配置
`appendonly`字段为开启/关闭AOF
```bash
appendonly no
```
`appendfsync`字段为修改AOF的写回策略
```bash
# If unsure, use "everysec".

# appendfsync always
appendfsync everysec
# appendfsync no
```
`appenddirname` 字段为AOF文件的保存路径文件夹，也与工作目录字段`dir`有关-->AOF相关文件存在dir/appenddirname/
```bash
# For convenience, Redis stores all persistent append-only files in a dedicated
# directory. The name of the directory is determined by the appenddirname
# configuration parameter.

appenddirname "appendonlydir"
```
`appendfilename`指定AOF文件名称
自Redis7后，使用**multi part AOF**机制（多部分AOF），将原来的依赖单个AOF文件的方式，改为由<u>BASE（基础）文件、INCR（增量）文件、MANIFEST（清单）文件</u>共同管理
```bash
# Append-only file names are created by Redis following a specific pattern.
# The file name's prefix is based on the 'appendfilename' configuration
# parameter, followed by additional information about the sequence and type.
#
# For example, if appendfilename is set to appendonly.aof, the following file
# names could be derived:
#
# - appendonly.aof.1.base.rdb as a base file.
# - appendonly.aof.1.incr.aof, appendonly.aof.2.incr.aof as incremental files.
# - appendonly.aof.manifest as a manifest file.

appendfilename "appendonly.aof"
```
例如上面配置，就会在dir/appenddirname/下，生成1个appendonly.aof.base.rdb、1个或多个appendonly.aof.incr.aof、1 个appendonly.aof.manifest（RDB+AOF混合的情况）


## 多部分AOF讲解
1. base文件，保存某个时间点AOF**重写后的Redis数据集**
2. manifest文件，记录AOF文件的名称、序号、类型等等
3. 在incr.aof系列文件中，**存储了每条写指令**

### AOF重写

当写指令不断增多，AOF文件持续增长，AOF文件会变的异常庞大，这时可以用AOF重写机**制压缩AOF文件**，具体方式与当前的持久化机制是RDB+AOF还是纯AOF有关
AOF重写可以**自动触发**或**手动触发**，若要自动触发，需要同时满足redis.conf中的下面两条配置：
```bash
auto-aof-rewrite-percentage 100 # 当前AOF大小是否比上次重写增加了100%
auto-aof-rewrite-min-size 64mb # 当前AOF文件是否到64MB
```
若要手动触发，可以用`BGREWRITEAOF`命令主动触发AOF重写
#### 纯AOF
若当前Redis没有开启AOF+RDB的混合模式机制，即`aof-use-rdb-preamble no`，base文件的后缀就是.aof，当满足重写要求时，会进行以下操作：
1. **创建重写子进程**： Redis 创建子进程，子进程根据当前内存中的数据集生成新的BASE.aof文件，不读取旧 AOF 文件。
2. **记录重写期间的写操作**： 主进程继续处理客户端请求，并将重写期间的新写操作写入新打开的增量 AOF 文件。原有有效文件集在切换前继续作为可靠的恢复基础。
3. **生成新的文件清单**： 子进程完成基础文件后，主进程收到通知，将新基础文件和增量文件登记到临时 manifest 中，并持久化该清单。
4. **切换到新文件集**： Redis 原子切换 manifest，使新文件集正式生效；旧的基础文件及不再需要的增量文件随后被清理。

 AOF 重写不是重新解析旧 AOF 并删除历史命令，而是**根据当前内存数据重新构建一份精简的基础数据表示**，再利用增量 AOF 衔接重写期间发生的修改。（读取旧AOF是Redis6的行为）

![AOF重写](image/Redis持久化机制_20261018164813/AOF重写.png)
#### AOF+RDB混合模式
官网推荐的Redis持久化方式是**AOF+RDB混合模式**，也就是在开启RDB、AOF的同时，再设置
`aof-use-rdb-preamble yes`
在混合持久化时，会优先使用AOF进行数据恢复，若没有AOF文件，再去找RDB文件
![AOF+RDB混合持久化](image/Redis持久化机制_20261018164813/AOF+RDB混合持久化.png)
对于开启混合模式后的AOF，会用**RDB镜像做全量持久化**，**AOF做增量持久化**
每次AOF重写生成的base文件，后缀会变为.rdb，即将最新的数据存储为新的RDB记录。
这样的话，重启服务的时候会从RDB和AOF两部分恢复数据，**既保证了数据完整性，又提高了恢复数据的性能**
![AOF重写时文件发生的变化（混合模式）](image/Redis持久化机制_20261018164813/AOF重写时文件发生的变化（混合模式）.png)

## AOF异常恢复
若正在写入AOF文件时，服务器宕机、磁盘空间不足等原因中断，AOF文件内就会有不符合格式的错误命令，此时可以用Redis自带的修复工具`redis-check-aof`修复
下面故意插入一条错误命令（20行）
```bash
*2
$6
SELECT
$1
0
*3
$3
set
$2
k1
$2
v1
*3
$3
set
$2
k2
$2
v2
zelda Nb
```

此时重启redis-server，会报错连不上
这时用`redis-check-aof --fix`命令修复AOF文件
```bash
[root@learn-linux appendonlydir]# redis-check-aof --fix appendonly.aof.2.incr.aof 
Start checking Old-Style AOF
AOF appendonly.aof.2.incr.aof format error
AOF analyzed: filename=appendonly.aof.2.incr.aof, size=91, ok_up_to=81, ok_up_to_line=20, diff=10
This will shrink the AOF appendonly.aof.2.incr.aof from 91 bytes, with 10 bytes, to 81 bytes
Continue? [y/N]: y
Successfully truncated AOF appendonly.aof.2.incr.aof
```
原来20行的那句"错误命令"就会被删掉
## AOF优缺点
优点：
1. 通过AOF文件记录写操作命令，**数据可读性较高**
2. 控制数据同步到磁盘的频率，例如，everysec 通常每秒同步一次，在性能和数据安全性之间取得平衡，**比RDB更好的保证了数据不丢失**
3. **支持AOF重写**，生成恢复当前数据集所需的精简记录，减少冗余命令
4. **可做紧急修复**，若不小心用了`FLUSHALL/FLUSHDB`这种命令，只需要在incr.aof文件中将该命令删掉，就可以恢复数据

缺点：
1. AOF记录写操作，而 RDB 保存的是某一时刻的数据集快照。对于大量重复修改同一个键的场景，AOF 可能包含许多可以被精简的历史命令，因此通常**比对应的 RDB 文件大**。
2. Redis重启恢复数据时，AOF 文件越大，恢复可能越耗时
3. 同步磁盘/AOF重写会**影响磁盘IO性能**

# 纯缓存模式
不管RDB还是AOF，都会有**开销**，若Redis只用来加速数据库查询，真正数据仍保存在MySQL，就可以**关闭持久化**，可以省去相关的磁盘写入，这就是纯缓存模式
要禁用RDB+AOF，在配置中配置这两个字段的value：
```bash
save "" # 禁用RDB自动触发
appendonly no # 禁用AOF自动触发
```
注意：即使禁用AOF+RDB的自动触发，依然可以通过`SAVE`/`BGSAVE`/`BGREWRITEAOF`手动触发
