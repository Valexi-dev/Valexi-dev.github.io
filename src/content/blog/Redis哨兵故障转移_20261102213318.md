- **主观下线（sdown）**：
指的是**单个Sentinel实例对服务器做出的下线判断**。
Sentinel每隔一段时间就会给Redis发送`PING`心跳包，检查存活状态。（可通过配置文件内`sentinel down-after-milliseconds`参数修改，默认30s）若在一定时间内没有收到合法回复，即当前 Sentinel 认为该节点下线
- **客观下线（odown）**：
指的是**所有 Sentinel 实例对服务器做出的下线判断**。
若只有一个 Sentinel 认为节点下线，那可能是因为自身网络原因导致无法连接，但如果多个 Sentinel 都认为节点下线，达到了`quorum`票数个，就会判定为该节点客观下线，会**开始后续的故障转移工作**

# 配置文件更新
在发生首次故障转移后，sentinel.conf会自动配置（重写）一些参数：
![sentinel.conf重写](image/Redis哨兵故障转移_20261102213318/sentinel.conf重写.webp)
Sentinel 在故障转移、发现其他节点等过程中，会**更新相关状态**，并将其**持久化到配置文件**。

这也是为什么明明配置文件一样，还要有多份sentinel.conf：redis-sentinel 在运行中可能会对配置进行 rewrite, 修改文件内容. 如果用一份文件, 就可能出现修改混乱的情况.

故障转移后，redis.conf们并不会变化，sentinel修改的是节点们的运行时配置，不会持久化到硬盘中

# 选举新主节点流程
Sentinel之间选举领导者的机制有点类似于**Raft算法**：
假定一共三个哨兵节点, S1, S2, S3
1. 每个哨兵节点都给其他所有哨兵节点, 发起一个 "拉票请求". `(S1->S2, S1->S3, S2 ->S1, S2->S3, S3->S1, S3->S2)`
2. 收到拉票请求的节点, 会回复一个 "投票响应". 响应的结果有两种可能, 投 or 不投.
> 比如 S1 给 S2 发了个投票请求, S2 就会给 S1 返回投票响应. \
> 到底 S2 是否要投 S1 呢? 取决于 S2 是否给别人投过票了. (每个哨兵只有一票). 
> 如果 S2 没有给别人投过票, 换言之, S1 是第一个向 S2 拉票的, 那么 S2 就会投 S1. 否则则不投.

3. 一轮投票完成之后, 发现**得票超过半数的节点, 自动成为 leader.**

> 如果出现平票的情况 (S1 投 S2, S2 投 S3, S3 投 S1, 每人一票), 就重新再投一次即可.
> 这也是为啥建议哨兵节点设置成奇数个的原因. **如果是偶数个, 则增大了平票的概率**, 带来不必要的开销.

4. leader 节点负责挑选一个 slave 成为新的 master. 当其他的 sentenal 发现新的 master 出现了, 就说明选举结束了.

Raft 算法的核心就是 "**先下手为强"**. 谁率先发出了拉票请求, 谁就有更大的概率成为 leader.

---

在选举出 Sentinel 领导者后，该领导者会在剩余的从节点中选出新的主节点，依据主要由三点：
5. 通过比较每个节点的**优先级**，优先级最高（值最小）的被选为新主节点
6. 若优先级相同，**比较复制偏移量**，偏移量最大（值最大）被选为新主节点
7. 若偏移量相同，**比较Run ID**，最小的选为新主节点。到这一步时只是为了让选举有确定性，而不是随机选择

其中优先级在节点配置文件的`replica-priority`参数
```bash
# By default the priority is 100.
replica-priority 100
```
Run ID：**Redis 启动时**会生成一个 40 位十六进制字符串作为 Run ID。

---
确定新主节点后，Sentinel 领导者首先向选中的从节点发送 `REPLICAOF NO ONE` 命令，**使其停止复制原主节点并提升为新的 Master**。随后，向其他从节点发送 `REPLICAOF <新主节点IP> <新主节点端口>` 命令，**使它们转而复制新的 Master**。

原 Master 恢复后，也会被重新配置为新 Master 的从节点，从而完成主从拓扑的切换。

# 哨兵缺点
虽然 主从复制+哨兵 可以自动故障转移，但<u>主节点宕机~故障转移完成之间的时间，写请求完全挂掉，这期间的数据会丢失</u>，这时就需要集群（cluster）来解决了
