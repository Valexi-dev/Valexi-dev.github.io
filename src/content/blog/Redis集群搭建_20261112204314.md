哨兵模式提高了系统的可用性. 但是真正用来存储数据的还是 master 和 slave 节点. 所有的数据都需要存储在单个 master 和 slave 节点中。如果<u>数据量很大，接近超出了所在机器的物理内存，就会出现严重问题</u>。（并且当master节点挂掉后的一段时间内，写数据会被丢弃，造成数据丢失）

要想存更大的数据量，就需要加机器。Redis集群(Cluster)就是这个思路：**引入多组主从复制，每一组只负责存储全集的一部分，从而构成一个更大的整体**

例如，下面示例中，有三台主节点，分别存数据全集的1/3，**集群（Cluster）内置了类似 Sentinel 的故障检测和自动故障转移能力**，因此当其中某个主节点宕机后，会**自动故障转移给从节点**
![集群](image/Redis集群搭建_20261112204314/集群.webp)
# 分片
在上面的实例中，**一个主从复制结构就是一个分片**，即有3个分片

决定数据在哪个分片，业界有三种解决方案：
1. **哈希取余**
假设集群由 N 个分片构成，对于任意一个 Key，先**对其进行哈希运算**，然后将**哈希值对分片数量 N 取模**，根据取模结果确定该 Key 应该存储在哪个分片中。
$$Shard(key)=Hash(key)\bmod N$$ 
![哈希取余](image/Redis集群搭建_20261112204314/哈希取余.webp)
**优点**：
实现简单，计算效率高。
能够将数据较为均匀地分布到各个分片（取决于哈希函数）。
**缺点**：
扩容或缩容时，分片数量 N 发生变化，原有的 Key 与分片之间的**映射关系会被大量破坏。**
需要重新计算数据归属，并迁移大量数据，导致较大的**网络、磁盘 I/O 和计算开销。**
2. 一致性哈希
将整个哈希空间映射到一个首尾相连的圆环上，称为**哈希环**。假设哈希空间为 $0$ ~ $2^{32}-1$，数据按照顺时针方向递增。
	- **节点映射**
将各个分片的主机名或 IP 地址作为哈希输入，计算其在哈希环上的位置：
$$
Position(node)=Hash(node)\bmod 2^{32}
$$
![哈希环](image/Redis集群搭建_20261112204314/哈希环.webp)
	- **Key映射**
当需要写入或读取 Key 时，通过哈希函数计算 Key 在哈希环上的位置：
$$
Position(key)=Hash(key)\bmod 2^{32}
$$
从 Key 所在位置开始，沿**顺时针方向**寻找遇到的第一个分片，该分片就是 Key 所属的分片。
![哈希环中key确定分片的方法](image/Redis集群搭建_20261112204314/哈希环中key确定分片的方法.webp)
	- 数据归属
每个分片负责<u>从其前一个分片（不包含）到自身位置（包含）的顺时针区间。</u>
![哈希环中分片所管辖的区域](image/Redis集群搭建_20261112204314/哈希环中分片所管辖的区域.webp)
	- 扩容
新增分片后，新分片只需要<u>接管其负责区间内原本属于顺时针后继节点的数据</u>，因此**只需要迁移部分数据**，而不需要重新计算所有 Key 的归属。
![一致性哈希扩容分片](image/Redis集群搭建_20261112204314/一致性哈希扩容分片.webp)
	- 缩容或节点宕机
节点下线后，其负责的数据按照哈希环规则**由顺时针方向的下一个节点接管**。但数据能否正常读取取决于是否存在可用副本。
![哈希环中节点宕机](image/Redis集群搭建_20261112204314/哈希环中节点宕机.webp)
	- 缺点
节点在哈希环上的**分布可能不均匀**，导致部分节点负责的数据范围过大，**产生数据倾斜**。
节点宕机后，虽然路由规则可以继续工作，但如果没有副本，仍然可能发生数据丢失或不可用。
3. 哈希槽
为了解决上述问题 (搬运成本高 和 数据分配不均匀), Redis 集群（cluster）引入了哈希槽 (hash slots) 算法，**设定16384个槽位（slot）**，通过下面算法来决定指定key在哪个槽位（其中CRC()也是一个算法）
$$
hash\_slot = CRC16(key) \mod 16384
$$
相当于是**把整个哈希值**, **映射到 16384 个槽位上, 也就是 [0, 16383]**。
然后再把这些槽位比较均匀的分配给每个分片。每个分片的节点都需要记录自己持有哪些分片
如果有三个分片，一种可能的分配方式是：
	- 0 号分片: [0, 5461], 共 5462 个槽位
	- 1 号分片: [5462, 10923], 共 5462 个槽位
	- 2 号分片: [10924, 16383], 共 5460 个槽位

> 这里的分片规则是**很灵活**的. **每个分片持有的槽位也不一定连续**. 每个分片的节点**使用 位图 来表示自己持有哪些槽位**。
> 对于 16384 个槽位来说, **需要 2048 个字节(2KB) 大小的内存空间表示**.

当扩容分片时，只需要让原先3个分片内都分出一部分槽位给新分片，缩容同理
![哈希槽扩容节点](image/Redis集群搭建_20261112204314/哈希槽扩容节点.webp)

但Redis 集群**不保证强一致性**（Strong Consistency），因此在故障转移过程中，已经向客户端确认成功的写入操作，也有可能丢失
# 哈希槽疑问

==既然槽位有 16384 个，分片是不是也越多越好，最多开到16384个？==

并非如此，实际上**Redis官方文档建议节点数量通常不超过1000个**。若分片只有3个，每个分片的服务器配置较高。
即使其中一个槽位恰好对应了系统中访问量极大、或者数据量极大的热点 Key，对于负责这个槽位的服务器来说，其他槽位就没有多大访问量，可以起到**“对冲”和“均摊”**的作用，整个节点承受的总负载会趋于平均
![均匀分配负载](image/Redis集群搭建_20261112204314/均匀分配负载.webp)

但如果有16384个分片，每个分片只管理1个槽位，每一台服务器都只能买**配置极低、微型的机器**（因为每个机器只分到一个槽位，分到的活很少）
当其中一个槽位恰好对应了系统中访问量极大、或者数据量极大的热点 Key，因为它本身的硬件资源（内存、CPU）极其有限，连个缓冲的余地都没有，瞬间就会被秒杀
![最大化分片](image/Redis集群搭建_20261112204314/最大化分片.webp)

==为什么是 16384 个槽位？==
**为什么不更多？**

沿用 Redis 作者 Antirez 在 GitHub 上的话来说，是**因为集群使用位图（Bitmap）记录每个节点负责哪些哈希槽**
每一个哈希槽对应一个 bit：
- 1：该节点负责这个槽。
- 0：该节点不负责这个槽。
假设有 16384 个槽：
$$
16384\div 8=2048\ Byte=2KB
$$

也就是说，**每个节点只需要 2KB** 就能表示自己负责的全部槽位。

如果使用 65536 个槽：
$$
65536\div 8=8192\ Byte=8KB
$$

槽位配置就会增加到 4 倍。

这些槽位信息会通过 Redis Cluster Bus 的 PING、PONG 等消息在节点之间传播。<u>如果每个节点携带的**槽位信息过大**，就会**增加集群通信开销**。</u>

并且Redis官方也规范，分片最好在1000个以内，因此16384个槽位完全够用

**为什么不更少？**
Redis Cluster 扩缩容时，**迁移的基本单位是哈希槽**（Hash Slot），而不是单个 Key。因此，**槽位数量会直接影响数据迁移和重新分配的粒度**

Redis Cluster 固定有 16384 个哈希槽，每个 Key 通过 CRC16 算法计算后，会被映射到其中一个槽位：
- **一个槽位可以包含多个 Key**。
- 一个槽位不是一个 Key。
- 同一个槽位中的所有 Key 都归属于同一个 Master 节点。

假设有100万个 Key，2个 Master: A, B，每个 Master 负责一半的数据，现在需要扩容 Master C，需要将一部分数据从 A, B 中迁移到C。

如果有10个槽位，假设每个槽位平均包含 10 万个 Key。我们希望只迁移 5 万个 Key，而一个槽位平均有 10 万个 Key，那么就**无法通过完整槽位的重新分配来实现这么细的调整**
![10个槽位下分片分配](image/Redis集群搭建_20261112204314/10个槽位下分片分配.webp)

如果是有1000个槽位，平均每个槽位 $1000000\div1000=1000$个key，现在就可以通过调整槽位数量，**更精细地控制每个 Master 负责的数据量**。
![10000个槽位下分片分配](image/Redis集群搭建_20261112204314/10000个槽位下分片分配.webp)

Redis 选择 16384 个槽位，就是**为了在数据分配粒度和集群通信开销之间取得平衡**。

==之后使用客户端连上集群中的任意一个节点，都相当于连上了整个集群吗？==
如果直接`redis-cli -p 6371`连接上其中一个主节点：
```bash
127.0.0.1:6371> set k1 v1
MOVED 12706 172.30.0.103:6379

127.0.0.1:6371> set k2 v2
OK
```
Redis Cluster 采用**去中心化架构**，客户端可以连接集群中的任意一个节点。

当客户端向某个节点发送命令时，该节点会根据 Key 计算对应的哈希槽，并判断该槽是否由自己负责。
- 如果由自己负责，则直接执行命令。
- 如果不由自己负责，则**返回 MOVED 重定向响应，告知客户端正确的目标节点**。

`redis-cli`**不会自动处理 MOVED 重定向响应**
要想自动将k1路由到对应节点，需要在连接客户端时**加上`-c`选项**，表示以集群方式连接，**使客户端自动处理 MOVED 和 ASK 重定向**，从而实现跨节点访问：`redis-cli -p 6371 -c`

便于理解的解释（不是真正原理）：不加 -c 选项就相当于单独访问一个节点，加上-c选项就相当于在上层加了一个总线节点，所有数据都通过该节点路由到下面的具体节点
