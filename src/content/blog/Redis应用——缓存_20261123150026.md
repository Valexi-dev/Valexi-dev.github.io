例如在一个软件中，用户每次打开个人主页，都需要查询自己的用户信息
```sql
SELECT * FROM user_info WHERE uid = 1001;
```
如果有 10 万名用户，每个人每天访问 20 次，那么数据库每天需要处理：
$100000 \times 20 = 200w$ 次查询

在这过程中，MySQL需要**反复查询大量重复数据**，并且当并发访问量很大时，**数据库可能成为整个系统的性能瓶颈**
因此需要缓存

# 旁路缓存模式
在现代后端中，**MySQL 作为持久化数据层，Redis作缓存层**，当用户发起查询后，业务层会先去Redis缓存层找数据，如果找到直接返回；如果找不到，再去 MySQL 查询，写入Redis并返回
![Redis+MySQL 缓存架构](image/Redis应用——缓存_20261123150026/Redis+MySQL缓存架构.webp)
- **Cache Hit（缓存命中）**：Redis 中存在所需数据，直接从 Redis 获取。
- **Cache Miss（缓存未命中）**：Redis 中不存在所需数据，需要查询 MySQL，再将数据写入

这样，只需要在 Redis 中放 20% 的热点数据, 就可以使 80% 的请求不再真正查询数据库了（二八定律）

## 更新数据

上面是读取数据的情况，如果是更新数据，同时也要**更新缓存中的数据**，否则再直接读缓存的数据就是 "**脏数据"** 了。但是如果直接写数据库并且写 Redis, 此时万一有一方写入失败, 就容易出现**数据不一致**的情况

### Redis逻辑

Redis采用**延时双删**
遇到需要修改数据的情况时，会先**删除Redis中的缓存**，再**更新数据库**，再次**删除缓存数据**

==为什么需要删除两次？==

考虑一种并发情况：
1. 服务器 A 删除 Redis 缓存。
2. 服务器 B 查询 Redis，发现缓存不存在。
3. 服务器 B 查询 MySQL，但读到的还是旧数据。
4. 服务器 A 更新 MySQL，写入新数据。
5. 服务器 B 将旧数据重新写入 Redis。
此时 Redis 又出现了脏数据。

因此，服务器 A 延迟一段时间后再次删除缓存，**可以清理服务器 B 可能重新写入的旧数据**。

注意：**延迟双删不能绝对保证强一致性**，延迟时间也需要根据业务的读写耗时合理设置。

### Canal（开源工具）

还有一种思路是**删除缓存重试**，只在更新数据库后进行删除，但**如果删除失败，会一直重试**
执行流程：
1. 先删除 Redis 缓存。
2. 如果删除失败，将失败的 Key 放入 MQ（消息队列）。
3. 后台消费者不断重试删除操作，直到删除成功。
![删除缓存重试](image/Redis应用——缓存_20261123150026/删除缓存重试.webp)
这就是阿里巴巴开源的 Canal 

==为什么通常选择删除缓存，而不是直接更新缓存?==
假设两个应用服务器同时修改同一个用户：
- 服务器 A 修改姓名为李四。
- 服务器 B 修改姓名为王五。

如果两台服务器分别更新 Redis 和 MySQL，由于两次操作并**不是原子操作**，**执行顺序可能交错**，最终造成 Redis 和 MySQL 的**数据不一致**。

而采用删除缓存的方式：
- 修改数据库。
- 删除缓存。
- 后续读取时重新从数据库加载数据。

就不需要在**每次修改时都精确维护 Redis 中的数据内容**。

这也是为什么实际业务中经常采用 **Cache Aside Pattern（旁路缓存模式）**

# 缓存更新策略
## 热点数据 
热点数据就是**在一段时间内被频繁访问的数据**，判定热点数据的方法有两种：
1. 定期生成
定期统计一段时间内的数据访问频率，挑选访问次数最高的前 N% 数据作为热点数据
![定期生成](image/Redis应用——缓存_20261123150026/定期生成.webp)
例如搜索引擎：
	- 平时大家经常搜索天气、新闻。
	- 春节期间，大家可能集中搜索春晚。

	通过定期统计，就能发现高频搜索词。

	缺点：**实时性较低**，如果突然出现热点事件，定期统计可能无法及时发现。
2. 实时生成
这种方式不需要提前统计热点数据，而是让 Redis 在运行过程中逐渐形成热点数据。

	基本流程：
	1. 给 Redis 设置内存容量上限。
	2. 用户每次查询，先查询 Redis。
	3. 如果命中，直接返回。
	4. 如果未命中，就查询数据库，并将结果写入 Redis。
	5. 如果 Redis 内存满了，就通过淘汰策略删除一部分数据。

	经过一段时间运行后，Redis 中自然会留下相对热门的数据。

	这种方式的特点是：**热点数据会随着实际访问情况动态调整**。

	如果缓存已经满了(达到上限), 就触发缓存淘汰策略, 把一些 "相对不那么热门" 的数据淘汰掉。
按照上述过程, 持续一段时间之后 Redis 内部的数据自然就是 "热门数据" 了.
## 缓存淘汰策略
假设 Redis 最大内存限制为 1GB，现在已经使用了 1GB。
此时又需要写入一个新的 Key：
```sql
SET user:info:10086 "张三"
```
Redis 应该怎么办？

如果一直允许写入，内存就会不断增长，最终可能导致系统内存不足。
因此需要**设置内存上限**，并配置缓存淘汰策略。
Redis 可以通过配置文件中的`maxmemory`设置最大内存：
```sql
maxmemory 1gb
```
当达到内存限制时，Redis 根据淘汰策略处理数据。

1.  **FIFO（First In First Out）：先进先出**
淘汰最早进入缓存的数据
2. **LRU（Least Recently Used）：最近最少使用**
淘汰最近一段时间内最久没有被访问的数据
3. **LFU（Least Frequently Used）：最不经常使用**
淘汰访问次数最少的数据
4. Random：随机淘汰
从缓存中随机选择一个 Key 删除

![缓存更新策略](image/Redis应用——缓存_20261123150026/缓存更新策略.webp)
## Redis内置淘汰策略
通过配置文件中的`maxmemory-policy`字段，可以设置缓存容量与缓存淘汰策略
```bash
maxmemory 1gb # 设置最大内存 1GB
maxmemory-policy allkeys-lru # 设置内存淘汰策略 【在所有 Key 中使用 LRU 淘汰】
```

| 策略 | 含义 |
| :--- | :--- |
| `noeviction` | 不淘汰，内存不足时新写入操作报错 |
| `allkeys-lru` | 在所有 Key 中使用 LRU 淘汰 |
| `allkeys-lfu` | 在所有 Key 中使用 LFU 淘汰 |
| `allkeys-random` | 在所有 Key 中随机淘汰 |
| `volatile-lru` | 在设置过期时间的 Key 中使用 LRU 淘汰 |
| `volatile-lfu` | 在设置过期时间的 Key 中使用 LFU 淘汰 |
| `volatile-random` | 在设置过期时间的 Key 中随机淘汰 |
| `volatile-ttl` | 在设置过期时间的 Key 中优先淘汰剩余 TTL 较短的 Key |
 - allkeys：所有 Key 都可以成为候选对象。
 - volatile：仅设置了**过期时间**的 Key 可以成为候选对象。

# 缓存问题
Redis 的作用是**替 MySQL 承担大量查询请求**。如果 Redis 无法提供缓存服务，大量请求就可能直接落到 MySQL 上
## 缓存穿透（Cache Penetration）
缓存穿透指的是：**访问的 Key 在 Redis 和 MySQL 中都不存在**。
假设有人不断请求一个不存在的用户 ID，每次请求都会经历 Redis --> MySQL-->返回空结果

这样 Redis 就无法发挥缓存作用，MySQL 需要承担大量无效查询
![缓存穿透](image/Redis应用——缓存_20261123150026/缓存穿透.webp)
可能会产生缓存穿透的原因：
- 业务设计不合理：缺少必要的参数校验，非法 Key 也被拿去查询。
- 开发/运维误操作：数据库中的部分数据被误删。
- 黑客恶意攻击：大量请求不存在的 Key。

解决方法：
1. **严格校验请求参数**
例如用户 ID 必须是正整数：
    ```cpp
    if (uid <= 0)
    {
        return;
    }
    ```
	如果查询的是手机号，还应该校验手机号格式是否合法。
	这样可以在请求进入数据库之前，拦截一部分非法请求。
2. **缓存空对象**
如果 Redis 和 MySQL 都没有数据，也可以将空结果写入 Redis。

	例如：
	```bash
	SET user:info:999999 "" EX 300
	```
	这里设置 5 分钟过期时间。

	下一次请求：
	```bash
	GET user:info:999999
	```

	虽然获取到的是空字符串，但我们知道这个 Key 对应的数据不存在，就不需要再次查询 MySQL。这种方式也叫**空值缓存**。

	注意：空字符串需要和真正的数据区分开，业务代码必须正确识别。
3. **布隆过滤器**
	布隆过滤器结合了 Hash 和 Bitmap 的思想，可以使用较少的空间**判断某个元素是否可能存在**
	它的特点：
	- **如果判断不存在，那么一定不存在**。
	- 如果判断存在，那么可能存在，也可能误判。

	这样可以在查询 Redis 和 MySQL 之前，提前过滤大量不存在的 Key
	
	想详细来了解布隆过滤器可以看下面这篇文章：
	[【数据结构】哈希——位图与布隆过滤器](https://blog.csdn.net/suimingtao/article/details/149122269)
## 缓存雪崩（Cache Avalanche）
缓存雪崩指的是：**短时间内大量 Key 在缓存上失效，导致数据库压力骤增，甚至直接宕机**
可能会产生缓存雪崩的原因：
- **Redis挂了**：例如 Redis 服务所在服务器突然宕机，导致缓存整体不可用
- **大量 Key 同时过期**：例如在某个时间段批量缓存了 10 万条数据，并且设置了相同的过期时间，那么它们可能在同一时间附近大量失效
![缓存雪崩](image/Redis应用——缓存_20261123150026/缓存雪崩.webp)

解决方法：
1. **部署高可用 Redis 集群**
例如使用 Redis Cluster 或 Redis Sentinel，提高 Redis 服务的可用性。

	即使某个 Redis 节点发生故障，也可以通过故障转移等机制降低服务不可用的风险。

	同时完善监控和报警体系，及时发现 Redis 故障。
2. **设置随机过期时间**
不要让大量 Key 使用完全相同的过期时间，而是在原有过期时间上增加随机值
例如：
	```bash
	int expireTime = 3600 + rand() % 600;
	```
	**让缓存过期时间分散**，避免大量 Key 同时失效

	或者可以**不给 Key 设置过期时间**，但这需要考虑 Redis 内存容量和数据淘汰策略

## 缓存击穿（Cache Breakdown）
缓存击穿可以理解为缓存雪崩的一种特殊情况。

区别在于：
- 缓存雪崩：大量 Key 同时失效。
- **缓存击穿：某一个热点 Key 突然失效**。

例如软件里的一个活动很热门，每秒有1w个用户访问，如果该key突然过期，会有几万个用户同时去访问MySQL内的该数据，造成缓存击穿
![缓存击穿](image/Redis应用——缓存_20261123150026/缓存击穿.webp)

解决方法：
1. **热点 Key 设置永不过期**
通过统计分析，发现哪些 Key 是热点 Key，不设置过期时间。

	这样热点 Key 就不会因为 TTL 到期而突然失效。

	当然，如果业务数据发生变化，仍然需要设计**主动更新或删除缓存的机制**。
2. **使用分布式锁限制数据库并发**
假设 10000 个请求同时发现缓存失效，我们可以**让它们竞争一把分布式锁**，这样就可以避免大量请求同时访问 MySQL。

	这里的核心思想是：**通过互斥机制控制重建缓存时访问数据库的并发数量**。

	实际开发中，还需要处理锁超时、锁释放和等待请求超时等问题

## 缓存预热（Cache Preheating）
假设 Redis 刚刚启动，里面没有任何缓存数据，这时候大量用户开始访问系统，MySQL 可能突然承受很大的压力。

因此，我们可以在系统正式提供服务之前，**提前将热点数据加载到 Redis 中，这就是缓存预热**。

例如系统每天早上 8 点开始运行，我们可以提前将用户经常访问的活动信息加载进 Redis，这样用户访问时，Redis 已经有了对应的数据
随着程序运行，热点数据还可以逐渐自动调整
## 热Key（Hot Key）问题
Redis 中的热 Key（Hot Key）问题，是指**某个 Key 在短时间内被大量客户端频繁访问，导致该 Key 所在的 Redis 节点负载过高，甚至成为整个系统的性能瓶颈**

例如，在一个总共有10 万 QPS的系统中，其中 8 万 QPS 都在访问 product:1001 数据，由于 Redis Cluster 使用 CRC16 哈希算法计算 Key 对应的哈希槽，一个 Key 只能属于一个哈希槽，而一个哈希槽只能由一个主节点负责。

因此，product:1001 的请求**会集中到同一个主节点**。
![热Key](image/Redis应用——缓存_20261123150026/热Key.webp)
这就会产生几个问题：
1. 单个 Redis 节点 CPU 使用率过高。
2. 网络带宽被大量请求占用。
3. Redis 响应时间增加。
4. 其他 Key 的访问也可能受到影响。
5. 严重时可能导致 Redis 节点无法正常提供服务。

核心问题：**请求集中在一个 Redis 节点，无法充分利用集群中其他节点的资源**。

解决方法：
1. **本地缓存**
**在应用服务器中增加本地缓存**，例如使用 C++ 的 LRU Cache、Java 的 Caffeine 等
这样在客户端请求Redis之前，会先去应用服务器本地缓存寻找

	例如第一次访问时：
	1. 本地缓存未命中。
	2. 从 Redis 获取商品信息。
	3. 将商品信息保存到本地缓存。
	4. 后续请求直接从本地缓存读取。
这样就能显著减少 Redis 的访问压力。

	优点：
	- 减少 Redis 网络请求。
	- 降低 Redis 节点负载。
	- 响应速度更快。

	缺点：
	- 多台应用服务器之间存在**缓存一致性**问题。
	- 需要考虑缓存过期和更新机制。

2. Redis多副本缓存
由于一个 Key 在 Redis Cluster 中只能归属于一个主节点，因此可以**将热点数据复制成多个不同的 Key**
	```bash
	SET product:1001:1 "商品信息"
	SET product:1001:2 "商品信息"
	SET product:1001:3 "商品信息"
	SET product:1001:4 "商品信息"
	```
	通过负载均衡，将请求分散到不同的 Key
![多副本缓存](image/Redis应用——缓存_20261123150026/多副本缓存.webp)
注意：
	- **复制出来的 Key 必须通过哈希计算分布到不同主节点，不能只是假设它们一定分散**。
	- 需要维护多个副本之间的**数据一致性**。
	- 适合**读多写少**的热点数据。
3. **使用读写分离**
Redis **主从复制**可以将读取请求分发到不同的 Redis 节点
让该主节点的**从节点们负责处理读操作请求**，主节点只负责写操作

	此外，如果所有请求仍然集中在同一个主节点，而不是分散到其副本，那么仅仅增加从节点并不能解决热 Key 问题。

4. **为热 Key 单独部署 Redis 集群**
如果某个热 Key 的访问量特别大，可以为它单独部署 Redis 集群。

	这样就可以把热点业务的访问压力和普通业务隔离开。

	优点：可以独立扩容、独立监控，也不会直接影响普通业务的 Redis 集群。

	缺点：增加服务器成本、部署复杂度和维护成本。
